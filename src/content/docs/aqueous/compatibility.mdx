Aqueous is a wlroots 0.20 compositor with native Wayland clients and optional
embedded XWayland. Its shell and tooling interfaces are protocols rather than
hard-coded dependencies on a particular desktop shell.

## Application and rendering protocols

Aqueous exposes the Wayland core compositor, subcompositor, shared-memory,
seat, output, and data-device interfaces together with:

- XDG shell, activation, decoration, foreign relationships, viewporter,
  fractional scale, single-pixel buffers, cursor shapes, alpha modifiers, and
  explicit content type.
- Linux DMA-BUF and explicit DRM synchronization where the renderer/backend
  support them.
- Presentation timing, tearing control, FIFO v1 commit pacing, and
  `commit-timing-v1` per-commit deadlines. Both renderer paths are implemented;
  physical DRM/VRR, scanout, and plane-promotion timing qualification remains
  outstanding.
- XDG dialogs, toplevel dragging, toplevel icons, and client-provided toplevel
  tags/descriptions. Dragging uses the integrated per-seat drag-and-drop path;
  external-policy mode hides that global. Tags can be used in window rules.
- Color representation and color-management-v1, including parametric image
  descriptions and the supported Windows HDR descriptions in the Vulkan
  effects build.
- `xdg-system-bell-v1` version 1 for configurable visual feedback and custom
  sound effects. It is available in Vulkan and Pixman builds, including
  security-context clients and external-policy mode. See
  [System bell](/aqueous/system-bell/) for configuration and request handling.

The default client-buffer policy advertises exact fractional output scale.
`integer-ceil` is an opt-in global or per-window compatibility path for
toolkits that produce softer output at fractional device coordinates.

For native HDR games using Proton-CachyOS, follow the
[Steam HDR setup](/aqueous/outputs/#hdr-in-steam-games-with-proton-cachyos),
including enabling HDR on the output and setting the game's launch options.

## Desktop shells and portals

Standard shell and desktop components can use:

- wlr layer shell for panels, launchers, notifications, and wallpapers.
- `ext-workspace-v1` for per-output workspace lists and activation.
- ext and wlr foreign-toplevel protocols for task lists and window discovery.
- The Aqueous window-info protocol for layouts, content type, detailed states,
  scene snapshots, decoration negotiation, and overlay diagnostics.
- wlr output management, output power, gamma control, and XDG output.
- ext idle notification, idle inhibit, and ext session lock.
- XDG desktop portals through the packaged wlr/GTK portal configuration.
- `ext-background-effect-v1` for exact client-requested blur regions in Vulkan
  effects builds, including compatible DMS/Quickshell clients.
- The versioned Aqueous shell protocol and persistent `AQUEOUS_SOCKET` IPC for
  state and typed runtime actions. See [Shell integration](/aqueous/shell-integration/).

Layer-shell exclusive zones feed directly into each output's usable area.
Session-lock surfaces are handled outside ordinary window policy and Auto HDR.

## Client and server decorations

Aqueous implements `xdg-decoration` mode negotiation. With
`[layout].force_ssd = true`, a client that creates an xdg-decoration object is
configured for server-side decoration even when it requests client-side mode.
Repeated client requests receive a configure response even when policy keeps
the same effective mode.

The legacy `org_kde_kwin_server_decoration_manager` is also available for GTK
and older Qt clients. Its display-wide default follows `force_ssd`.

Applications that do not create the protocol object—or that paint a custom
toolbar/title bar into their normal content—are not removable by compositor
policy. Use an application setting or a typed `[[application]]` launch profile
for those clients. See
[Rounded corners and decorations](/aqueous/visual-effects/#rounded-corners-and-decorations)
for configuration and diagnostics.

## Capture, sharing, and clipboard

Capture clients can use wlr screencopy and export-DMA-BUF, plus the newer ext
image-copy-capture protocol and output/toplevel capture-source protocols.
Clipboard tools are supported through core selection, primary selection, and
both ext and wlr data-control managers.

Overlay-plane candidates fall back to normal composition while capture or a
software cursor requires it, ensuring capture tools see the expected content.

The packaged `xdg-desktop-portal-aqueous` backend handles ScreenCast and
Screenshot with a session-selected source chooser; other portal interfaces use
the session's Pearl/GTK routing. See [portal setup and troubleshooting](/aqueous/shell-integration/#screen-sharing-and-portals).

See [Pearl clipboard and screenshots](/pearl/docs/clipboard-screenshots/) for
history and PNG saves, or [remote viewing and control](/aqueous/shell-integration/#remote-viewing-and-control)
for remote support limits.

## Input protocols

Aqueous supports relative pointer, pointer constraints, pointer gestures,
tablet v2, text input v3, input method v2 and its popup surfaces, virtual
pointer, virtual keyboard, XWayland keyboard grabs, and compositor-side idle
notification. Holding the configured `untrap_pointer` binding temporarily
releases a client pointer constraint and restores it when the key is released.

Physical tablets support per-output absolute pen mapping through
[`input.toml` tablet rules](/aqueous/tablets/), with independent mouse input.
Drawing clients need tablet-v2 support; this does not add mouse emulation for
applications without native tablet support. Physical HUION/Wacom calibration
and XWayland drawing-application compatibility still require device testing.

`keyboard-shortcuts-inhibit-v1` lets eligible focused clients inhibit normal
compositor bindings. Built-in virtual-terminal switching remains reserved.
`pointer-warp-v1` supports client cursor repositioning after checks on focus,
client ownership, a recent pointer-enter serial, coordinates, grabs, and constraints.

## XWayland

When built with `-Dxwayland=true`, Aqueous starts and manages XWayland itself.
Rules match X11 `WM_CLASS` through `class`, and `aqueousctl` reports the X11
backend and identity. Aqueous integrates X11 focus, transient relationships,
fullscreen, maximize/minimize, floating geometry, and validated
`_NET_WM_MOVERESIZE` interactions.

XWayland scaling defaults to **legacy**. If you manage your session's compositor
command, add `-xwayland-scaling native` to `aqueous` (or `aqueous-git` for the
[separate Git session](/aqueous/desktop-session/)), then log out and back in.
Adding the flag to the packaged `aqueous-wm` wrapper does not work: it does not
forward arguments. Do not launch a second compositor inside the running
session. Remove the flag or use `-xwayland-scaling legacy` to undo it.

Native mode keeps XWayland on the renderer-selected GPU and projects it per
output. Restart the app and check it on each display. Texture filtering is a
separate setting and does not set an X11 app's DPI. `-no-xwayland` disables
XWayland and its applications for that session.

If a game opens on the wrong monitor, use a
[window rule to choose its monitor](/aqueous/window-rules/#open-an-xwayland-game-on-a-specific-monitor).

### Troubleshoot soft text

1. Run `aqueousctl windows --json` and find the app by its window title.
   `backend: "xwayland"` means XWayland; `"xdg"` means native Wayland. Match the
   window's `output` to a monitor in `aqueousctl outputs --json` and check its
   `scale` (`1` means 100%).
2. If an XWayland app looks soft when enlarged on a scaled display, try the
   app's native Wayland mode if available. Otherwise, try native XWayland
   scaling as described above if you control the compositor command. Compare
   the same app on the same monitor.

On Vulkan-effects builds that include
[PR #163](https://github.com/Seafoam-Labs/Aqueous/pull/163), the default
[`scale_filter = "auto"`](/aqueous/configuration/#state-and-client-scaling)
already uses high-quality filtering when shrinking a buffer. The setting is
not available in Aqueous v1.1.0. It does not add detail when enlarging a window
or when the buffer already matches the screen pixel for pixel.

If you set the global filter to `bilinear` or `nearest`, you can restore
high-quality downscaling for one XWayland app. Copy its actual `class` from
`aqueousctl inspect --rule` and add this to `rules.toml` before broader matches,
or add `scale_filter` to the app's existing rule:

```toml
[[window]]
class = "ExampleClass"
scale_filter = "high-quality"
```

Save to reload the rule, then compare the same view on the same monitor.
Remove `scale_filter` from the rule to inherit the global filter again.

In [#149](https://github.com/Seafoam-Labs/Aqueous/issues/149), Chromium was
already running natively on Wayland at 100%. XWayland settings do not apply,
and `integer-ceil` still requests scale 1 at 100%. There was no confirmed
fix for that case.

## Games and application stalls

[Game Mode](/aqueous/layouts/#game-mode) anchors a window and leaves space for
companion windows. It does not enable fullscreen, VRR or a performance service.
Use the game's own fullscreen setting to test fullscreen behavior.

For crashes, freezes or low frame rates:

1. Record the app/version, Proton build, graphics API, Wayland or XWayland
   backend, Aqueous version, GPU/driver and output mode.
2. Note the trigger: loading, fullscreen, focus/workspace change, offscreen
   movement or capture. Does only the app freeze, does input stop, or do other
   displays keep updating?
3. Collect `aqueousctl windows --json`, `aqueousctl outputs --json` and the app's
   log while the session responds. See [diagnostics](/aqueous/command-line/).
4. Change one setting at a time and keep its previous value. For a total input
   freeze, arrange an independent recovery console before trying to reproduce it.

These closed reports document earlier symptoms:

| Symptom                                                             | Existing report                                                                                                                |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| MPV playback slows the desktop                                      | [#44](https://github.com/Seafoam-Labs/Aqueous/issues/44): closed without reproduction.                                         |
| Fullscreen game freezes and input stops while other content updates | [#103](https://github.com/Seafoam-Labs/Aqueous/issues/103): the reporter no longer reproduced the freeze after a Steam update. |
| Proton native-Wayland scRGB HDR colors spill into other channels    | [#104](https://github.com/Seafoam-Labs/Aqueous/issues/104): the reported scRGB path was fixed in Aqueous v1.0.19.              |

An offscreen crash needs diagnosis before a keep-active rule. Focus, suspension,
frame callbacks, rendering and process liveness are different states. No general
keep-active, Proton or driver-reinstallation fix is established for these reports.
For sharing lag, use [capture diagnostics](/aqueous/shell-integration/#sharing-is-slow-black-or-frozen).

## GPU selection and multi-GPU systems

At startup Aqueous resolves the DRM device used for scanout/rendering and
exports compatible client-selection variables when appropriate. This keeps
clients and the Vulkan renderer on the same device in hybrid-GPU setups. The
Vulkan effects build requires the renderer and the pinned wlroots render hook
to expose the required integration.

## DRM leasing

`drm-lease-v1` is implemented for non-desktop DRM connectors, including the
connector class used by VR headsets. Aqueous reserves these outside desktop
output handling and revokes leases on lock/session changes. Availability depends
on the backend and hardware; security-context clients are restricted.

Protocol and headless tests pass, but physical DRM/VR qualification remains
outstanding. Protocol support alone is not a claim that a headset has been tested.

## Aqueous extension protocols

- [Screen warming](/aqueous/screen-warming/) provides exclusive per-output
  adjustments and commit/restoration status for eligible SDR Vulkan outputs.
- [Input activity](/aqueous/shell-integration/#input-activity) supplies authorized
  category-only keyboard/mouse press notifications to Pearl.
- [Capture color metadata](/aqueous/shell-integration/#isolated-window-capture)
  describes the destination encoding of supported isolated window captures.

## Known protocol gaps

`ext-transient-seat-v1` remains unavailable, so clients cannot create temporary
independent seats through that protocol. The legacy wlr input-inhibitor
protocol is also unavailable; use an ext-session-lock client for screen locking.
Superseded generations of xdg-foreign, tablet, input-method, and text-input
remain omitted in favor of their supported modern interfaces.

The [source protocol inventory](https://github.com/Seafoam-Labs/Aqueous/blob/master/docs/missing-protocols.md)
tracks implementation and qualification limits. Registry availability can vary
with build, renderer, backend, and client policy.

<Aside type="note">
  General Plasma- and GNOME-private shell APIs are not implemented beyond the
  legacy decoration compatibility described above. This does not prevent
  standard Wayland applications from running, but desktop components that
  require compositor-specific private APIs need a protocol-compatible
  alternative.
</Aside>
